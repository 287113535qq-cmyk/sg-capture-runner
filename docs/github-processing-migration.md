## 运行分工

- 两个现有 GitHub 仓库保持每组最多 20 个采集分片，可用节点先工作。每个分片在 GitHub 内执行玩法、规范化、结算、日志与恢复判断。
- 游戏唯一归属、批次分配、租约更新、错误分类、暂挂及继续下一款的算法全部在 GitHub。测试服不得运行 campaign/pool/TrialStore，也不得进行 Python/Node 玩法复算、SQLite 日志或 JSONL 导出。
- 测试服仅提供受限 SSH 数据通道、轻量只读系统指标和 MongoDB 原生读写。只有固定库/集合、有限大小批次及规定数据库操作可通过；无任意 shell、脚本、查询执行或生产库访问。
- `official_rounds` 仍只保存原样完整局，原 `_id`、contentHash、序号、计划、会话及已核验历史保留。不会将队列或未完成局伪装成完整记录。

## 必须持久保存的运行状态

GitHub-hosted Runner 临时磁盘不能独立承担跨运行恢复。用户已经明确选择允许在**现有** `sg_capture_staging_v1` 内新增两个纯数据集合：

| 集合 | 数据 | 运算位置 |
|---|---|---|
| `capture_state_v2` | 游戏归属、批次范围、版本号、租约、检查点与暂停原因 | GitHub 计算新状态，Mongo 仅执行带版本条件的原子更新 |
| `capture_journal_v2` | 请求意图、原始响应、未完成局、待写完整记录和恢复证据 | GitHub 生成、验证及恢复；Mongo 仅存取 |

两个集合均不属于生产游戏池，不计入完成量。记录必须携带可信账号分组和既有 trial/worker 标识；受限入口按已有 SSH 分组验证访问边界。新集合的唯一索引、版本条件和持久写入确认用于防止跨节点重复分配，不在服务器实现业务调度。

本次确认扩展了旧规则中仅允许 `official_rounds` 的存储范围，新增范围仅限上述两个辅助集合。`official_rounds` 继续只保存完整局；辅助状态不计入完整局数量，不扩大到生产库、其他集合或公共明文 artifacts。

## 资源暂停

GitHub 每 10 秒采样测试服 CPU 和基于 MemAvailable 的内存使用率，每批写入前判断；任一达到 95% 或指标超过 30 秒无效即暂停提交。两者低于 90% 连续 60 秒后小批量恢复，并限制恢复速率。数据库错误和人工暂停不会随资源下降而解除。

受限服务器入口只返回 `/proc` 计数和存储空间，CPU 差值、比例、恢复窗口及节流判断均由 GitHub 计算。已有写入确认未知时先读回同一记录再幂等补写。无法保证响应持久化时停止新源端请求，不通过积压继续无限采集。

## 切换验收

1. 确认两个仓库无活动/排队任务，旧 worker/batch 租约无活动；只读核验旧 queue/pool/batch 和 Mongo，单独保留所有未知在途意图。
2. 完整私有备份并固定摘要；迁移计算和旧记录/原始字段审查在 GitHub 执行，服务器只导出旧文件及数据库数据。
3. 测试资源迟滞、采样失效、未知写入读回、内容冲突、跨组隔离、重复请求、租约丢失、节点中断、待写上限和跨运行恢复。
4. 单独授权和部署受限 Mongo 数据通道，旧业务 RPC 保持关闭。验证只读、写入与恢复行为，明确新版和旧版不能同时写。
5. 受控短采、全文核验及当前故障独立恢复证据通过后才恢复正式运行。不得仅因 SSH 恢复或新增代码通过离线测试而打开采集开关。
