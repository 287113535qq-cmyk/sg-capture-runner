# GitHub 采集数据库往返优化

用户要求当前游戏完整采集后再优化，通过验证后继续后续游戏。32723、32726 均已完成 299850 个新采全文终审，加各 150 个已核验历史，达到每款 300000；累计完成 8 / 178 款。下一批游戏先置为临时 operator-wait，原计划、归属、会话和目标未修改。

## 优化范围

实现 `04d38e4b72011fc600634146031334f9a8440a3c`：

- 在一次固定 Mongo 查询中读回两组共同暂停状态、当前组 campaign 和当前 trial pool；保护判断仍在 GitHub。
- 分片保存自己上次成功 CAS 后的批次版本。后续写入仍使用该版本做条件更新，冲突或确认未知即停止；不能覆盖其他操作者的改动，也不自动重放请求。
- 每次新源请求前读取最新控制和租约状态；租约需要续期时才做 CAS。
- 每批最多 100 条日志改为有界批量读回；完整内容核对、Mongo 全文读回及检查点确认均保留。
- 增加数据库调用次数与耗时统计，供实际瓶颈分析；统计不包含敏感请求或会话值。

测试服只增加 `control_read`、`read_many` 两个受限读操作，没有接回任何玩法、调度、恢复或结算算法。原数据授权清单的哈希、11 个 trial 范围、三个隔离集合和关闭的历史导出权限均未改变。

每次 SG 请求的意图和完整响应仍分别可靠持久化。未知请求不重发，未完成自然玩法保留后暂挂，CPU / 内存任一达到 95% 的写入暂停及恢复迟滞保持。

## 离线验证与性能边界

Windows / GitHub Linux 全量 209 项 Python、41 项 runner-v2 Node 测试通过；GitHub 另通过采集器、旧协议 Node、TypeScript 和 3000 局离线集成。[预检 36466216460](https://github.com/zyzuoyang/sg-capture-runner/actions/runs/36466216460) 不发送 SG 请求。

同一 100 局单帧离线夹具中，批次处理数据库调用从 1220 次降至 518 次，减少 57.54%。旧版读 812 次，新版读 108 次加 2 次批量读；两版都保留 304 次 CAS、100 次不可变日志创建、3 次完整局读回和 1 次批量插入。该夹具使用简化控制层，数字用于定位重复交互，不是完整生产链路的调用总数，更不是官方采集吞吐量或提速百分比。

此前实际采样的官方请求平均耗时约 27–36 ms，而迁移后的完整处理每款约 3350 局 / 分钟，说明不能将慢速直接归因于 SG 响应。还需用新版本的实际窗口判断数据库、标准化和免费链占比，不能承诺所有游戏恢复到 30 分钟。
