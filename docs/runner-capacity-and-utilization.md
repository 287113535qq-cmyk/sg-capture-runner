# 20 台机器并发与持续采集效率

最新状态：动态分批已接入实际采集与存储链路，并通过 Linux 上的 20 路并发完整链路测试。见 [dynamic-pool.md](dynamic-pool.md)。下面保留并发容量诊断和初期组件验证的历史过程。

## 已经证实的结果

2026-09-28 北京时间进行的独立诊断，实际取得了 20 台不同的 GitHub-hosted Linux Runner。20 台执行探测程序的共同在线窗口为 **178.766 秒**。这不是把 20 个排队任务当成 20 台运行机器。

- 运行：[36332950026](https://github.com/zyzuoyang/sg-capture-runner/actions/runs/36332950026)。
- 每台的开始、心跳和结束时间：[runner-capacity-result.json](runner-capacity-result.json)。
- 官方游戏接口请求：0；数据库写入：0。这项结果仅证明 Runner 并发容量，不代表已经测得 20 会话的采集吞吐。

上一轮正式采集运行 36329489181 的确只有最多 16 台同时执行，分片 1、12、13、18 最初没有分配到 Runner，在前面的任务结束后才启动。工作流当时已经申请 20 路，没有配置 16 路限制。GitHub 的接口没有提供那次分配不足的具体原因；新诊断已排除“账号固定只能运行 16 台”的判断。

GitHub [标准 Runner 并发限制](https://docs.github.com/en/actions/reference/limits#job-concurrency-limits-for-github-hosted-runners)列出 Free 为 20。实际运行数仍应读取 Runner 和作业状态，不能仅凭工作流参数宣称 20 台同时采集。

## 采集启动检查

采集工作流已增加 `runner-readiness.mjs`。每台先完成依赖安装，再确认本次运行的全部 20 个采集任务进入就绪步骤。检查仅访问 GitHub 元数据，不访问游戏接口。3 分钟内不足 20 台时，本节点在调用游戏接口前结束并明确报告容量不足；不会把 16 路开跑报告成 20 路。

诊断工作流也复用相同启动检查，权限仅为仓库和 Actions 读取，没有采集凭据。它只能手动启动，不新增任何定时采集。

新检查已经在 [36333412006](https://github.com/zyzuoyang/sg-capture-runner/actions/runs/36333412006) 实际验证：20 台全部通过就绪检查，随后共同在线 **169.318 秒**，所有任务成功。每台时间及检查结果见 [runner-readiness-result.json](runner-readiness-result.json)。这次同样没有游戏接口请求和数据库写入。

该检查确认的是启动时全部节点到齐。开始后仍需用每个会话的租约和持续增长的完整局数验证真实采集并发，不能用就绪状态替代采集产出。

## 已发现的效率损失

正式采集每个节点均使用 0 毫秒人为请求间隔，长连接也已经复用。各节点领取约 1 万个固定局数，平均速度却从 **5.815 局/秒到 29.164 局/秒**不等。快节点约 6 分钟就结束，最慢节点需要约 30 分钟。

根据已保存的每台计时，慢节点的大部分时间用在官方响应和存储网络往返；服务端每次写入处理平均不足 9 毫秒。仅把并发参数设成 20，不能解决快节点提前做完后闲置的问题。具体计时见 [capture-utilization-analysis.json](capture-utilization-analysis.json)。这些节点的统计窗口不同，不能相加后当成实测总速度。

## 动态分批组件的最初验证阶段（历史）

`service/work_pool.py` 已实现并通过离线测试：

1. 将全局目标拆成小批次，每台完成并确认写入后继续领取。
2. 根据该节点完成速度调整下一批大小，接近终点时缩小批次。
3. 用事务保证 20 台同时领取也不会重叠局号，最终不超过目标。
4. 已领取的批次始终绑定原节点和原会话。连接恢复时返回原批次并要求恢复日志；不把未知结果的 BET 交给其他会话重发。
5. 只有可信服务端读取确认完整结算、日志、文件和数据库检查点全部成立，才允许将批次标记完成。
6. 故障停止新分配，保留已收到的数据，旧租约不能在过期后提交确认。

本节记录初期仅有独立组件时的状态。当时尚未接入采集 RPC；后续已经完成接入和端到端验证，详见上面的最新报告。新的实采目标仍需用户确定数量，不能把模拟测试称作官方采集已运行。

本机验证：86 项 Python 服务测试、8 项 Node 会话与就绪检查测试全部通过。离线模拟验证快节点能获得更多工作；模拟时间不作为官方接口的效率结果。
