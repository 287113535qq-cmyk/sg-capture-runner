## 保存与恢复

1. Runner 使用固定 SSH 主机指纹和受限专用 key 获取单游戏租约；只有当前 owner/epoch 能写。
2. 每次官方请求先记录持久化 intent；响应先写 SQLite 日志。没有可靠响应的投注请求绝不自动重发。
3. 完整局经 Runner 与服务器分别复核，原始与标准化 JSONL 按偏移追加并 fsync。
4. 每 100 局批量写 Mongo，使用唯一序号和操作身份。写入后逐条读回、比对完整内容，再推进 checkpoint。正常停止时不足 100 局的尾批也确认入库。
5. 中断恢复先处理已有日志及 Mongo 不确定确认。重复确认不增加条数；不同真实局即使结果相同仍保留为不同局。原协议 RID 是转轴组编号，不能用作唯一局号。
6. source HTTP 429 的 Retry-After 转为持久化冷却时间；该任务只有一个固定官方主机。源站/协议不确定状态停止续跑，需要核对后恢复。

服务器只处理存储和校验，不访问 SG。原始文件、SQLite 和 Mongo 均在隔离区域；不清空历史文件、游戏集合、finish 或 skip 标记，也不部署游戏服务。

## 运行与验收

`SG Book of Sevens 300k trial` 支持手动 capture / audit / status。先 1 局验证，再跨 Runner 继续 100/1000 局并校验，最后启动完整目标。单 Runner 最长采集 240 分钟后在完整局边界停止；定时任务接着同一 checkpoint 继续，累计达到 300000 后停止。

审计重新逐局读取持久文件，验证哈希、金额、类型、连续序号和 SQLite 一致性，核对 Mongo 总条数、序号边界、下注/返奖总额、免费与零返奖计数。Mongo 每个批次在推进 checkpoint 前已逐条比对完整文档。结果包含实际完整局每秒、官方请求延迟 p50/p95/p99、免费局数量、零返奖数量和最大倍率。运行中的估算速度不能当作 30 万局最终效果。

每次日志只记录脱敏统计；原始协议含会话字段，仅保存在服务器受限存储与隔离库。
