# 20 台持续采集：动态分批已经接入

这次优化把“每台固定分到约一万局”改为“20 台从同一个任务池领取小批次”。快节点完成并确认保存后继续领活，慢节点领取较小的批次；接近目标时进一步缩小批次，减少最后等待少数慢节点的时间。

## 已完成的链路

1. 同一个采集工作流启动 20 个 GitHub-hosted Linux 作业，等所有节点准备好。服务端也要求 20 个独立会话完成注册，才开始分配第一批。注册等待最多 3 分钟，缺少节点会明确停止；断开连接的空闲注册不会被算成在线节点。
2. 每台固定使用自己的会话、连接和恢复身份。领取批次使用事务，同时领取不会得到重复局号。
3. 首批最多 100 局，后续按该节点已完成批次的速度调整，目标约为 8 秒一批，通常为 20–400 局。收尾批次可以更小。
4. 一局中每个官方响应先保存到持久日志，免费局全部结束才算一个完整局。文件和数据库确认后，节点才能交还批次并领取下一批。
5. 节点跨批次复用源站会话、余额状态、SSH 通道和 Mongo 连接，避免每一批重新登录、初始化游戏或启动数据库进程。人为请求间隔维持 0 毫秒，每个会话始终只有一个在途请求。
6. 已领取但未完成的批次固定绑定原会话。未知结果不会换会话重发；免费局可以依据已经保存的响应继续恢复。
7. 目标全部确认后，服务端自动停止新分配；晚到的节点正常结束。最终统一核对原始文件、标准化字段和 Mongo 的完整内容；动态模式不再让每个节点各审计一次后又全量重复审计。

批次调度、官方采集循环、持久日志、数据库确认和恢复逻辑已经连接在一起，不再只是独立的分配器测试。源站请求仍仅能来自 GitHub-hosted Linux Runner，本机和存储服务器不发游戏请求。

## 已完成数据保持独立

原目标 `bookofsevens_300k_20260927` 的 300000 局和原分片配额保持不变。动态模式禁止复用这个 trialId；下一批需要一个新 trialId 和用户确定的全局局数。

`config/trial-pool.json` 目前为 `configured=false`，trialId 和目标局数未填。工作流仍关闭，原续跑变量仍为 false。本次优化没有新增官方局，也没有用模拟数据填充正式采集集合。

## 下一批的启用步骤

下面是操作人员步骤，不能在用户尚未确定下一批数量时执行启用：

1. 在 `config/trial-pool.json` 填入新的 Book of Sevens trialId、已确定的目标局数，并设 `configured=true`。保留普通下注 `buy=0`、成本 0.25、免费类型 `bonus=1` 和 20 会话约束。
2. 提交并部署同一份配置。Runner 和服务端会核对配置哈希；已经创建的目标不能中途改数量或业务规则。
3. 使用服务器操作员命令 `python3 service/pool_operator.py enable` 启用这个新目标。公共 RPC 没有启用、修改配额或清除异常的入口。
4. 在原有 `trial-300k.yml` 工作流选择 `allocation=dynamic`、`role=capture`。动态模式固定 20 个作业，使用配置中的全局目标；`round_limit` 仅供旧固定分片模式使用。
5. 如需恢复原有定时续跑，先明确配置 `SG_TRIAL_ALLOCATION=dynamic`，再启用既有工作流和续跑变量。不要创建另一条采集定时任务。当前跟进自动化仍保持暂停。
6. 用根 RPC 的 `journaled/durable/checkpoint` 和各节点持续增加的实际局数判断进度。所有批次的确认数量相加才是总量；单个批次最大的局号不是完成数量。

末尾少量批次仍可能先后结束，网络和官方响应也会影响速度。优化的目标是有未分配任务时让节点继续工作，缩短慢节点造成的尾部等待；新的官方速度须由下一批实采测量。
