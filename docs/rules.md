# 连接、恢复与完成规则

## 2026-10-01 防止源前失败空转

正式会话身份必须绑定新运行owner及activation；拒绝旧会话是保护，不能删除历史账本来绕过。采集子进程非零退出后父进程结束并报告具体失败，不因池尚未标失败就无限重启。源前零分配失败只能在确认原文、注册、批次、计数及许可都未变化后，用独立不可变修订凭证切换代码；不重置目标或覆盖已应用profile。连接统计只做被动观测，缺事件记未知，阶段不重复相加，实测结果和优化预期分开。

## 2026-10-01 发布避免本机自动整理造成阶段等待

本地提交和推送显式使用`git -c gc.auto=0 -c maintenance.auto=false`，网络推送保留显式代理及30秒低速超时。自动整理不是发布前置条件；不因它拖延已经完成的提交。优化分别标记离线通过、Linux通过、已部署和线上实测，多会话内核测试不能代称源准入或实测提速。

## 2026-10-01 离线预检避开正在满负载采集的账号

运行统一Linux离线预检前，先只读核对两仓对应执行状态。同一账号已有20个采集job运行时，优先在已同步相同源码且有空闲容量的另一仓派发无源preflight，不让准备工作等待整轮采集结束。已派发但尚未分配Runner的本次重复预检，可在精确核对run/head/jobs后取消，再转移一次；不取消健康采集、不改源开关、不诊断或重派历史精确隔离queued。只读状态不自动授予源请求或业务维护权限。

## 2026-09-30 按已审核特征复用分析与修复

新款准备先运行 `scripts/feature_reuse_index.py --game <gameId>`，按协议、会话、请求链、计数和终局机制检索可复用部分。匹配必须列出差异与未核验分支，只补差异证据；不因名称、相同FID数字或同协议而复制整个适配器。未知款明确待分类，不能归入默认通用组授予准入。新修复验证后更新离线索引与规则卡；代码/客户端hash不变的已核证据复用。索引不修改生产队列、额度或已应用profile，匹配不代替独立金额、请求出口及新会话准入验证。

## 2026-09-30 用户重申：主线准备与修复队列同时执行

故障入队后必须实际安排修复，不能只创建 `pending-adapter` 记录便长期搁置。保持两条工作线：主线准备下一款并在准入通过后采集；修复线逐款完成队列中的适配、验证和重新准入。利用本机并行执行互不依赖的分析与检查，涉及共享文件、许可和线上状态的写操作仍串行。这里的进程并行不自动授权创建子代理。

- 每次进度明确列出正在修复哪款、已完成哪一步、剩余阻塞；入队、离线候选、修复上线、重新入正常队列分别报告，不能互相代称。
- 修复完成后必须接上重新入正常队列的动作，不能只交付代码。重入前验证独立 Python、Runner、collector、真实留样和受影响入口，并完成必要 Linux 检查、计数结清、新会话及有效许可准入。不得复用已作废会话、重置已用额度或借用已注销额度。
- 修复线不能等待当前主线候选准备结束；主线也不能等待旧款修好。某一步受阻时继续该线不依赖阻塞的工作，并处理另一条线；不得以报告或队列状态替代实际修复。
- 每轮开始和切换阶段时核对两条线的实际执行项：主线候选、正在修复的游戏、对应代码/检查结果、下一步及具体阻塞。修复队列非空且有可执行工作时，必须在本轮实际推进一款修复，不能再次只推进主线。只有入队记录、计划或状态标签，不算同步修复；没有运行进程时也不得声称有后台修复运行。
- 单款修复依次经过证据核验、代码修改、独立验证、必要部署及重新准入；验证未完成保持待修复，已验证但尚未重入明确标记待重新准入。只有实际回到正常队列才报告重入完成。旧半局和旧许可仍保持冻结。

本条落实用户此前已确定的方案。2026-09-30 核查时四款修复状态仍为 `pending-adapter`；当前首先推进 32795 免费重触发修复，其余 32714、32718、32636 逐款处理。没有通过验证和实际重入前，不称修复完成。

- 单轮连续推进最短可执行链路，不在每个小模块完成后停下，不把20分钟心跳当作下一阶段的启动条件。相邻阶段超过5分钟未推进时，记录具体阻塞、正在执行的命令及下一项可执行动作。
- 保留既有源请求、额度、租约、数据完整性、资源与空间保护；持续推进不表示可以跳过准入、重放旧BET、借用已注销额度或声称未经验证的成果。
- 明确区分“已完成”“正在运行”“被阻塞但仍有独立工作”“需要外部介入”；没有后台任务时不得说仍在运行。已有结论和未变化现场不反复测试、归档或通知。

## 2026-09-28 用户新增：CPU / 内存过载暂停写入

用户要求测试服 CPU 和内存超过 95% 时暂时停止写入，恢复后继续。按任一指标达到 95% 即触发保护执行，两个账号共同遵守：

- 以测试服整机指标为准。CPU 使用率取采样时间窗口内的实际忙碌比例，不以 load average 代替百分比；内存使用率按 `(MemTotal - MemAvailable) / MemTotal` 计算，不能把可回收缓存全部当成不可用内存。
- GitHub 侧每 10 秒取得轻量只读指标，在每批写入前检查。CPU 或内存使用率任一达到或超过 95%，停止提交新的 MongoDB 写入批次；采样失败或指标超过 30 秒未更新时同样暂停。测试服只提供系统指标，不执行调度、玩法复算或审计逻辑。
- 已发出的 MongoDB 写入不强行中断。GitHub 保存其确认状态；超时或断线不能视为写入失败，必须先按原记录身份读回核对，再决定是否幂等补写，不能重发原 SG BET。
- 恢复条件为 CPU 与内存使用率均低于 90%，连续保持至少 60 秒且指标有效，以避免在 95% 附近反复启停。只有资源过载这一暂停原因可以据此自动解除；恢复后先低并发提交待写批次，再按资源反馈增加写入量，不能同时倾倒全部积压。
- 待写记录在 GitHub 侧可靠保留，未确认写入不得推进已落库检查点或计入最终完成量。队列必须有容量上限；接近上限时停止新 BET，不能丢弃记录或无限累积，也不能只依赖 Runner 临时磁盘跨任务保存。

- 数据库连接使用 SG 服务实际生效的 `.config-cache/mongo-config-*.json`；它覆盖旧 YAML 和容器初始化值。缓存文件可能只有管理员可读，普通账户看不到不能据此断言不存在。
- 所有运行时缓存应指向同一已核实连接；每款游戏的数据库名从对应运行配置读取，集合为 `simulate`。读取凭据只在受控进程内完成，不输出 URI/账号/密码。
- GitHub Runner 只通过固定主机指纹的 SSH 通道访问受控存储/Mongo；禁止开放 Mongo，禁止关闭 StrictHostKeyChecking。隔离测试链路已通过 Runner 网络及实际写入验证，凭据与正式游戏库分离；不能据此认定 SG 官方会话和正式导入已验证。
- 当前 Mongo 只读数量审计不是逐条身份校验，也不证明 sourceId 映射后的数据已经满足采集完成规则。
- 未知特殊类型默认 2000 局；已知特殊类型每种分别达到 special-limit，并覆盖要求的 free-choice 选项；是否同时要求普通局数遵从正式配置。历史 WMS 300000 大局批次是另一份范围记录，不自动替代本次目标。
- 完整 WMS 大局需完成所有实际 feature/free continuation 并到达 EndGame；失败的未完成大局不能计为完整数据。统计 JSON 行不等于已验证协议完整性。
- 先持久化原始及规范化完整局、幂等 Mongo 写入，确认成功后才能推进 checkpoint。不得清空旧 JSONL、Mongo、finish 或 skip ledger。
- 新增持久化队列必须原子 claim、绑定 run/job owner、续租并 fencing；只回收过期 lease。同游戏变体串行；429 Retry-After 跨 run 持久化。
- 当前允许已验证第一轮计划在 GitHub-hosted Linux Runner 上采集，并写入隔离暂存库；不写生产游戏池，不在本机或存储服务器执行官方采集。第二轮保持关闭。

## 每游戏分析留档（2026-09-29 补充）

每款游戏的分析与规则必须保存，方便后续复用。非敏感材料存入针对游戏 ID 的文档，并运行 `python scripts/build-game-rule-archive.py` 更新 `docs/game-rules/<gameId>.json` 和总索引；代码、协议、映射或分析证据变更时一并更新。档案记录大局开始/继续/完成条件、特殊环节字段、已知支持范围、未确认事项及代码/报告摘要，不能将 30 万局数量当全部玩法覆盖证明。

实际触发统计仅在已有全文终审中顺带计算，并在已授权的 `capture_journal_v2` 保存规则快照及观察摘要。不得增加源请求或为档案额外重扫已完成游戏；当前旧运行保持固定代码版本，后续新运行采用。原始协议和会话证据仅留在私有日志，公开档案不得含会话、PID 值、凭据或完整启动 URL。新增档案不改变已有验证、停采、资源保护和第二轮关闭规则。详见 [留档机制](game-rule-archive.md)。
