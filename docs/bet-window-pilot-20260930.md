# 效率优先：投注边界分局试点（Beaver32820）

## 方案

把分局、推进协议、详细玩法分析拆成三层。通用层将同一会话的一次成功普通BET及其后续免费/选择/奖励帧放进同一大局；下一次成功普通BET提供下一局起点。实时发新BET仍须先有上一局已结算的正面证据，不能试探投注。最后一局没有下一BET时，有明确终态才封口，否则保留pending。

游戏专用层只负责协议的下一动作与可普通下注状态，从原客户端实际状态机抽取，遇到未知分支暂停原局。详细bonus分类和玩法统计独立执行；金额、会话、完整性、持久化与Mongo全文读回继续是计数前必需检查。不能把尚未分类或未结算的原始帧直接计作完整局。

线上试点设计：先通过统一维护补写Beaver38并保留所有旧数据、暂挂Demon及其已耗尽许可，然后仅worker7续接原pending120，最多完成这一个原局、禁止新BET。成功后才允许另一个明确绑定的有限阶段，最多100新普通局（20worker各最多5），额度耗尽或遇未知/拒绝即退出，不连续增加额度。对同一份原始数据并行比较旧校验与新分局，不为A/B对照重复下注。该设计尚未生成线上许可或派发。

## 效率对比与结论

本机对同一100历史局，30次采样、每次20轮，记录每轮墙钟：

| 路径 | 中位数 | p95 |
| --- | ---: | ---: |
| 现有Runner下一步/结束校验 | 0.530毫秒 | 0.648毫秒 |
| 通用投注分组+客户端出口回放 | 0.923毫秒 | 1.083毫秒 |

这是两个原型路径的本机微基准，工作内容并非完全相同，不包含SG网络、持久化、Python审计、启动等待或备份。新原型未表现出CPU提速，不能称为采集吞吐提升。最初无通用输入检查的探索版约0.71毫秒，不能用它冒充最终带检查版本。

方案在已有样本上的分局可行性成立；预期收益是复用分组和恢复基础设施、缩小每款游戏适配范围，而非节省亚毫秒解析。开发耗时没有等条件对照，不能宣称已经缩短若干倍。下一步线上有限试点须记录源请求/控制查询/Mongo/健康等待/解析/总时长及完整局数；同一数据双路径结果一致才考虑替换旧入口，特殊样本不足必须标记未覆盖。

当前状态：离线试点完成，线上试点未执行；原Demon446和Beaver38+pending120不变。实际首测事件总线桩少了一层函数，修正桩的调用形状后完成回放，没有改原客户端函数或放宽结束条件。
