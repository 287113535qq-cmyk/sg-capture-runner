## 执行顺序和验收

1. **当前事故已收敛。** 两个明确拒绝218/440已统一完成一次独立审查与归档；不再逐个复制操作器、分别发布。旧267局、所有旧回执保留，新凭证独立绑定新事故、运行和版本。本次按worker0/13/14分别4/0/5、其余各10完成179局，原总200额度全部用完。原218已被拒绝，不能要求其原attempt完成或把它当自然免费终局证据；需要新独立完整自然免费证据、全部旧替代及446全文验收才能正式放行。
2. **把恢复变成经过测试的统一执行器。** 事故配置明确列出“保留、补写、明确拒绝归档、原局接续、剩余额度”，阶段凭证依旧不可复用。验收必须经过实际 `campaign.select → worker admission → continuation → flush → quota → validate` 入口，并覆盖两个并发拒绝、阶段中断、旧任务出现和租约冲突。仅操作器内存测试通过不能发版。
3. **提前完成玩法状态表。** 从现有官方客户端和历史全文整理普通、免费、嵌套、重触发、选择、终态、金额规则；Python/Runner/TS使用同一组公开合成输入但保留独立验证实现。尚不明确的内外层计数转换、最大赢额退出等必须显式标记；合成终局不能替代真实SG证据。
4. **让单款问题与全队列进度分开。** 仅未适配自然功能、无未知在途时，按审核流程保留pending并安全暂挂，再推进已ready游戏。现在ready为0，必须同时把8款暂挂、155款待适配按已有真实样本和完成难度排序；优先形成下一款可采候选。Beaver已有隔离集成保留，但未通过真实免费终局，不能直接算ready。源端拒绝/存储异常仍须先消除共同保护原因，不能靠切游戏绕过。
5. **减少控制往返和重复留档。** 同一边界的独立GitHub状态读取并发执行；祖先回执用有界批量读取，保持完整覆盖和每条绑定检查。已有持续SSH通道继续使用。不可变历史证据用内容哈希引用已验证双份备份，新归档只增加本次新增证据；两端实际读回仍保留。优化前后分别测请求数、耗时和故障交错结果，不对在跑固定版本热改。
6. **用分项计时判断下一步。** 持续记录源请求、解析CPU、Mongo往返、调度排队、资源等待、维护和全文审计的p50/p95。目标是缩短发现分支到完成适配及安全恢复的周期；不承诺未经测量的倍数。时间超限触发复盘和安全切换任务，不触发自动删局、重放或解除保护。

当前职责继续保持：GitHub执行采集和业务验证；测试服提供原生Mongo及系统指标。只有实测证明解析CPU成为主要瓶颈时，再评估迁移收益和数据库资源竞争。当前优先改恢复流程、入口测试和适配排期。
