## 字段含义

| 字段 | 规则 |
| --- | --- |
| bet | 整局实际投注成本；从整数金额证据核算，再除以100。购买、加注的实际扣款不能被普通基础投注额替代。 |
| mul | 整局总返奖除以实际投注成本；零返奖为0，零成本或不明成本拒绝。 |
| buy | 普通投注0；购买类型1、2、3、4、5等；加注模式11、12、13、14等。编号来自每款游戏固定的模式映射。 |
| bonus | 普通数据0；不同免费数据类型1、2、3、4、5等。编号来自每款游戏固定的免费类型映射。 |

buy 和 bonus 独立。普通投注自然触发免费数据，可以是 buy=0、bonus=2；加注后未进入免费数据，可以是 buy=11、bonus=0。免费数据没有返奖时 bonus 仍保留其类型，mul 为0。

不再使用“freeGame=1、feature=2、freeFeature=3”的全局 bonus 编号。primaryBonusKind 只是流程描述，特殊功能不会自动变成 bonus=2；同一种流程下的不同免费选项可以有不同 bonus 编号。无法识别的游戏、购买/加注模式或免费类型直接拒绝，不填0冒充普通局，也不按本批次出现顺序重新编号。

## 分析与保存

1. 原始协议、局前余额和来源类型映射进入离线分析器。NextGen 使用最终 TW 和已对齐的 B/AB；WMS 只接受声明为每次 Logic 返奖的适配规则，累计到完成的 EndGame，并与起始 stake 及余额对账。
2. NextGen 采集器生成的 bet/mul/buy/bonus 与服务器共用的 Python 分析器结果交叉核对。WMS 通过同一个 Python 分析器准备标准化数据。
3. Runner 将原始证据和计算结果传给受限 SSH 服务。服务器使用本机发布目录中的类型配置重新分析，拒绝字段篡改、未知映射、未完成免费流程和金额矛盾。
4. 校验通过才写入持久化日志、原始/规范化 JSONL 和暂存 Mongo。Mongo 文档顶层及 normalized 中均保存 bet/mul/buy/bonus；不只存在日志里。
5. Mongo 确认后推进进度；验收时重新计算并核对文件、日志和 Mongo，最后复制到隔离 accepted_rounds。重复提交/导入不会新增记录。

类型配置为 `service/round_types.json`，必须按游戏来源建立固定映射，并绑定配置哈希。当前只登记了明确标记 fixtureOnly 的两个测试来源；它们不是178款真实游戏的已审阅模式表，也不能用于真实游戏。真实游戏必须提供协议选择器与类型编号的对应证据，才可新增其映射。多种不同免费类型同时出现而没有整体分类规则的局会拒绝，不自行拆局或任选编号。

`fixture_fields_` 批次强制业务字段校验，不能删掉字段绕过。之前的纯传输测试批次保持兼容，不回填或重写旧记录。真实采集入口及定时调度继续关闭。

## 验收范围

19条人工样本覆盖 NextGen/WMS，buy=0、1～5、11～14，bonus=0～5。包含自然免费、不同购买类型、加注、免费零返奖、单独特殊功能、混合流程和小数倍数。

手动工作流 `SG business field verification` 依次执行：错误字段拒绝 → Mongo落地后故意退出 → 新Runner恢复并逐条对照预期值 → 两次隔离导入。再次运行同一批次会跳过已完成的写入，只进行复核。实际 Actions 回执另存为 `business-fields-result.json`。

本次不证明任何真实官方会话有效，也不证明所有游戏的金额单位、WMS返奖累计方式及免费类型都已识别；不支持的证据会停止该条入库，等待补齐明确规则。
