# 两账号分配不同游戏：启动故障与调度改造边界

更新（2026-09-28 11:38 UTC）：用户随后明确授权“能启动的先用，排队的启动后再分配”。[可用分片启动及独立分组调度](available-workers-20260928.md) 已完成部署和受控迁移，第二组 20 个分片分批完成 200 局真实短采。下文是改造前的审查记录，其中“尚未执行”和 20 台集体门槛不再代表当前状态；新的停止来自 32717 自然功能协议校验。

## 启动检查不依赖游戏

`trial-300k.yml` 在执行 `campaign-worker.mjs capture` 前调用 `runner-readiness.mjs`。后者只读取当前 GitHub run/attempt 的 jobs，等待 20 个 `capture-N` 都进入启动检查；不读取游戏计划，不连接 SSH，不领取服务端批次，也不请求 SG。因此更换游戏、创建第二份目标或重建仓库不能直接修复这一步的 Runner 排队。

新增同一 workflow 的 `role=runner-check`，用于单独验证这一点：20 个标准 Linux Runner，只 checkout 和读取 GitHub jobs，不使用采集 Secrets、不配置 SSH、不访问 SG 或存储服务器。显式诊断等待 600 秒；正式采集仍为 180 秒。诊断不执行 verify，避免读取已暂停的 campaign 后再次关闭手动运行入口。运行结果另见 `secondary-isolated-runner-check-20260928.md`。

## 分配不同游戏可以隔离什么

现在 `service/campaign.py` 的 `control.active_game` 只有一个，两个仓库都调用同一个 `select`。某个活动游戏出现协议故障会暂停共享 campaign。要让两组各采一款，需要改服务端调度和受控迁移，不能只在工作流里填两个游戏 ID。

可实施的方案如下，尚未执行：

| 范围 | 需要的行为 |
| --- | --- |
| 账号身份 | 继续从受限 SSH wrapper 取得 primary/secondary，不能相信 RPC 自报身份。 |
| 活动游戏 | 每组有自己的活动游戏、审计租约和暂停原因；一款游戏同一时刻只能归属一组。 |
| 数量与历史 | 共用原 games 清单，每款只有一个累计 300000 目标；不复制历史基线、trial 或额度。 |
| 原会话 | primary 保持 worker 0–19 和原 HMAC/会话；secondary 保持 20–39；不能跨组接管未知 BET。 |
| 32714 | 保留原始记录、pending 和协议停采，不能通过调走游戏或删除自然触发将其标为解决。 |
| 新领取 | 第二组只领取经核验仍为 ready 且未分配的游戏；155 款 needs-adapter 和 protocol_holds 保持。 |
| 停采范围 | 单款协议错误只暂停所属组；空间、存储一致性等全局故障仍阻止两组新 BET。 |
| 不可变项 | 不修改 campaign config_hash、各 planHash、目标、历史计数和已有会话绑定；用另行审查的附加调度状态迁移。 |
| 验证 | 并发领取不得重复、跨组操作拒绝、暂停隔离、全局停采、终审后换游戏均需测试；部署前核对两仓库 jobs/租约并备份。 |

这项改造可以避免 32714 的协议暂停阻止另一组领取其他游戏，但无法为第二账号获得额外 GitHub Runner。应先用独立检查核实 Runner 分配，避免将两个问题混为一谈。当前没有应用上述迁移，没有领取第二款活动游戏，也没有恢复任一组采集。
