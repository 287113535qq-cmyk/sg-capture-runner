# 隔离链路验收

用户仍要求暂不采集真实局。本次接通的是 GitHub-hosted Linux Runner → 固定主机密钥的 SSH 入口 → 持久化日志/进度 → 独立 Mongo 暂存库 → 独立验收集合。SG 官方获取真实结果、导入现有游戏池仍未开放。

## 隔离边界

- 测试库固定为 `sg_capture_staging_v1`；集合只使用 `rounds` 和 `accepted_rounds`，不写178款游戏的 `simulate`。
- 写入账号只授予该库 readWrite。密码只保存在服务器600权限文件；GitHub不持有Mongo密码或管理员私钥。
- 新SSH账号 `sgcapture` 只能运行指定RPC入口，禁止交互shell、命令执行、PTY和端口转发。sudo只开放无参数的固定包装器；Python使用隔离模式，从root所有的固定发布目录加载代码。
- 只接受 `fixture_...` 测试批次、`fixture-...` 测试游戏及 `fixtureOnly=true` 的记录；正式数字游戏ID被拒绝。
- 一个RPC请求最大16KiB，一局最大8KiB，每批最多21个测试任务、每任务最多5条。这是链路测试服务，不是已开放的正式批量采集器。

## 保存顺序和恢复

1. 按游戏原子领取租约，保存owner、epoch、过期时间和心跳；有效租约不允许抢占。
2. 校验测试记录身份，将待保存记录和文件偏移写入SQLite持久化日志。
3. 追加原始及规范化JSONL并fsync。重复请求核对原偏移的内容；半行只允许补齐匹配的剩余字节，不清空文件。
4. 使用真实Mongo确认写入，依靠稳定身份和唯一索引去重。
5. 再次检查租约仍有效，最后在一个事务里确认记录并推进checkpoint。
6. 中断后从持久化日志恢复。失效的旧worker不能推进进度；同身份不同内容立即拒绝。
7. 比较JSONL、持久化日志、Mongo的数量、身份集合和完整内容；通过后才能复制到独立的验收集合。重复导入不增加记录。

冷却时间持久化在测试批次中，重启后不能被缩短。正式采集的官方主机级限流、全局队列和真实session逻辑还需另外接入，不能把测试批次冷却当成已完成的SG限流验证。

## 手动工作流

- `seed`：一条写入和重复提交；第二条在Mongo确认后故意退出进程，此时checkpoint仍停在第一条。
- `resume`：另一台Runner接手，恢复第二条再写第三条，并核对一致性。
- `workers`：20个矩阵任务，每个1款独立测试游戏，各2条记录。
- `audit`：最终43条测试记录，通过原始/规范化/Mongo一致性检查；独立验收集合重复导入应新增0条。
- 对已完成的同一case再次运行：不重采、不重跑20个写入任务，只复核与重复导入。
